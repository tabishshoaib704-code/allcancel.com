# Deploying to GitHub Actions

The bot runs as a scheduled workflow. Credentials live in GitHub Secrets,
never in the repo.

## 1. Push the repo

Make it **private**. Even with secrets handled properly, your thresholds
and account structure aren't things to publish.

```bash
cd google_ads_bot
git init
git add .
git commit -m "Google Ads bot"
git remote add origin git@github.com:<you>/<repo>.git
git push -u origin main
```

`.gitignore` already excludes `google-ads.yaml`, `bot_config.yaml`,
`reports/`, and `logs/`. Confirm before your first push:

```bash
git status --ignored | grep google-ads.yaml
```

If `google-ads.yaml` ever does get committed, rotating the refresh token
is mandatory — deleting the commit is not enough, since it stays in the
history and in any clone.

## 2. Add secrets

Repo **Settings → Secrets and variables → Actions → New repository secret**:

| Secret | Where it comes from |
|---|---|
| `GOOGLE_ADS_DEVELOPER_TOKEN` | Google Ads UI → Tools → API Center |
| `GOOGLE_ADS_CLIENT_ID` | Google Cloud Console → OAuth 2.0 credentials |
| `GOOGLE_ADS_CLIENT_SECRET` | Same OAuth credential |
| `GOOGLE_ADS_REFRESH_TOKEN` | Generated by Google's OAuth flow |
| `GOOGLE_ADS_CUSTOMER_ID` | The account the bot manages, digits only |
| `GOOGLE_ADS_LOGIN_CUSTOMER_ID` | Only if you access via a manager/MCC account |

Generate the refresh token once, locally, using Google's
`generate_user_credentials.py` from the google-ads-python examples repo.
It's a one-time interactive browser step — it can't be done inside CI.

## 3. Commit your thresholds

`bot_config.yaml` is gitignored by default, so the workflow falls back to
copying `bot_config.yaml.example`. Two options:

- **Keep it ignored** and edit the `.example` file with your real
  thresholds (leave `customer_id` as a placeholder — the secret overrides
  it at runtime). Simplest.
- **Un-ignore it** by removing that line from `.gitignore` and committing
  the real file. Cleaner separation, but puts your CPA targets in the repo.

Either way, leave `dry_run: true` until you've reviewed real reports.

## 4. First run

Go to **Actions → Google Ads Bot → Run workflow**, pick **report-only**.
This pulls metrics and policy alerts without invoking the rule engine at
all — the safest possible smoke test that your credentials work.

Then run **dry-run** and read the report in the run summary. The full
report is also attached as a downloadable artifact for 30 days.

## 5. Going live

Two independent gates must both be open:

1. `dry_run: false` in `bot_config.yaml`
2. The workflow run uses mode `live`

The scheduled daily run always uses dry-run — a cron trigger passes no
input, and the workflow defaults it to dry-run. Live runs are manual only
unless you change that default. Given the previous suspension on this
account, keeping the schedule read-only and applying changes by hand is a
reasonable long-term setup, not just a starting posture.

To require approval on live runs: **Settings → Environments → New
environment → `production`**, add yourself as a required reviewer. The
workflow already targets that environment for live mode, so live runs will
then pause until approved.

## Things that will bite you eventually

- **Schedule drift and disabling.** GitHub's cron can lag under load, and
  it disables schedules on repos with no commits for 60 days. If the bot
  matters, check that it's still running monthly.
- **Refresh token expiry.** Tokens for apps in OAuth "Testing" status
  expire in 7 days. Publish your Cloud Console consent screen to
  "In production" or you'll be regenerating constantly.
- **API version deprecation.** `bot/client.py` pins `v18`. Google retires
  versions on a schedule; when it goes, every run fails at once. The
  failure-issue step will tell you.
- **Failure notifications.** The workflow opens a GitHub issue when a run
  fails, which emails you through normal notification settings. Verify
  your GitHub email notifications are actually on.
